# Libretro core information

`colortvgame_libretro.info` in the repository root is optional frontend metadata, named to match the built core. Copy it to the frontend's configured core info directory separately from the core library; directory locations and permissions depend on the frontend. The existing release and CI packaging scripts do not include it. An isolated RetroDECK RetroArch 1.22.2 test confirmed discovery and parsing, and the user confirmed Core Information and version 0.1.2 in the test session. This file does not imply libretro distribution or upstream acceptance.

The fields follow the key/value conventions in official libretro-super examples: [Nestopia](https://github.com/libretro/libretro-super/blob/master/dist/info/nestopia_libretro.info), [2048](https://github.com/libretro/libretro-super/blob/master/dist/info/2048_libretro.info), and [Mr.Boom](https://github.com/libretro/libretro-super/blob/master/dist/info/mrboom_libretro.info). Display name and corename identify this independent simulator; category `Game` reflects its built-in playable implementation rather than claiming hardware emulation. The project license is MIT. `supported_extensions` is `ctg`, and `supports_no_game` is true: the core accepts five-byte CTG selectors or starts its selector without content. `needs_fullpath` is false because the core reads content from memory.

Feature flags describe the implementation: save states, cheats, memory descriptors, libretro memory saves, subsystems, hardware rendering and disk control are unsupported; input descriptors and core options are provided. `libretro_saves = false` refers to the libretro memory interface, not the core's separately persisted preferences. The description and notes summarize its approximations, video requirement and lack of rewind; see the [content format](CONTENT_FORMAT.md), [research](RESEARCH.md), and [README](../README.md) for details. Historical game identities, availability, physics and presentation remain unverified; real-frontend and platform testing remains limited.

To try the draft without installing it, build the core and run `scripts/core-info-test.sh` from the repository (or invoke it by path from another directory). It starts a temporary copy of the built core without content, with a temporary copy of the info file and an appended configuration pointing RetroArch's core directory and core info path at those copies. Open **Information → Core Information** in RetroArch to inspect it. Set `CTG_FRONTEND=native` or `CTG_FRONTEND=retrodeck` to select a frontend; the default `auto` prefers native RetroArch, as in `scripts/launch.sh`. RetroDECK receives read-only access to the project and temporary directory. The temporary files are removed after the frontend exits, including on failure; `config_save_on_exit` is disabled in the appended configuration. This does not prevent the frontend or core from writing other files according to their normal settings. RetroArch's [core info source](https://github.com/libretro/RetroArch/blob/master/core_info.c) scans the core directory, matches info files by core ID, and sets the internal `HAS_INFO` flag when parsing succeeds; `has_info` is not a required `.info` field. Verbose frontend logs can help investigate discovery, but successful discovery does not establish that the UI displays the fields. An isolated 120-frame test using matching temporary directories produced a RetroArch core-info cache entry with `has_info = true`, the core name, `ctg`, and MIT. The user confirmed the Core Information screen and version 0.1.2 using the test launcher.

Author, database, system identifiers, firmware, and display version are omitted rather than inferred. Individual field recognition and display, especially `notes`, vary by frontend and have not all been checked. Run `python3 tests/core_info_tests.py` from any directory to check the metadata's syntax and selected declarations; this standalone test is not registered with CTest and does not validate frontend behavior or independently exercise the core.
